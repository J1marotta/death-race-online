Why Death Race Works

Death Race is a browser game about suspicion.

On the surface, it is twenty little racers moving toward a finish line. Underneath, it is a social deduction game wearing running shoes. Every human secretly controls one racer. Nobody gets a name tag during the race. Everyone gets one bullet. The real game is not "can I go fast?" It is "can I move just naturally enough that nobody realizes which one is me?"

That is the heartbeat of the project:

  • Hide in a crowd.
  • Read other people's movement tells.
  • Spend your one shot wisely.
  • Survive long enough for your racer to cross the line.

The rest of the engineering exists to protect that feeling. Everything on this page — the code panels, the demos, the bug stories — traces back to that one sentence.

The Plain-Language Version

Think of the game as three connected places:

  1. The arcade cabinet: the React app in the browser.
  2. The race office: the Cloudflare Worker API.
  3. The official clipboard: one Durable Object per room code.

The browser draws the track, handles keyboard and mouse input, and shows the lobby. The Worker receives room actions like "create", "join", "ready", "start", "shot", and "next round". The Durable Object is the single source of truth for one lobby. If room DRABCD exists, that room has exactly one official room object coordinating it.

That matters because multiplayer games get weird when every browser invents its own truth. If one player thinks Mia is ready, another thinks she is not, and the host thinks the room started already, the game stops feeling like a game and starts feeling like a broken group chat. The Durable Object is the referee holding the clipboard.

What We Built

The project is now a deployed multiplayer prototype, not just a local mockup. Players can:

  • Create a lobby and receive a shareable room code.
  • Join from another browser with a username and see the real connected roster.
  • Ready up; the game starts only when everyone is ready, and only the host can start it.
  • Enter the same countdown and playing state on every client.
  • Send live movement snapshots at 20Hz and shoot once per round.
  • Earn 3 points for winning a round and 1 point for killing another human player.
  • Share shot, kill, winner, scoreboard, and next-round state.
  • See a closed-room state if the host leaves or the room expires.

The current live loop is intentionally desktop/laptop first. Touch controls, accounts, permanent profiles, and ranked play can come later. Right now the important promise is simpler: a friend can open the site, type your code, join your lobby, ready up, and play.

How A Lobby Works

This is the exact flow the lobby had to earn. Step through it — the difference between a fake lobby and a real lobby is that every step changes the shared room snapshot, not just your screen.

  1. Host clicks Create lobby.
  2. The app generates a room code like DR1JLQ.
  3. The browser sends action: create to the Worker.
  4. The Worker routes that code to one Durable Object.
  5. The Durable Object creates a room with James as host.
  6. The host sees the room code and real player list.
  7. A friend enters their username and the code.
  8. The friend sends action: join.
  9. The room adds them as a connected player.
  10. Everyone sees the updated roster.
  11. Each connected player clicks Ready up.
  12. The Worker only allows the host to start when every connected player is ready.
  13. The host starts the countdown.
  14. Both browsers follow the same room phase into live play.

How Live Play Works

During live play, every browser still renders its own scene. That keeps the UI fast and simple. But important events are shared through the room:

  • Local movement sends input snapshots at 20Hz over the live socket.
  • The latest snapshots live in the room's memory and go out as compact 50ms deltas.
  • Shots are recorded in room state with killer and victim attribution.
  • Shot racers are eliminated for every client and freeze where they fell.
  • The room adjudicates human finish-line wins from the freshest inputs; the host reports NPC wins.
  • The shared scoreboard, kill counts, and round history come from the room.

The host still drives phase transitions, but the contested moments — who crossed first, who killed whom — are decided server-side from live input data. NPC wins still come from the host because NPCs are simulated deterministically on every client, and the server does not run that simulation.

For friends testing a hidden-identity party game, this architecture is the right kind of honest: real multiplayer rooms, clear state ownership, enough synchronization to play, and not too much infrastructure too early.

Why Sprint Costs Something

For most of the project's life, sprint was free: hold Space, go 1.5x forever. That made the optimal strategy degenerate — hold Space from go to finish — and a degenerate optimal strategy is poison for a hidden-identity game, because every human plays identically (flat out) and identically is exactly what NPCs don't do.

Sprint is now a stamina budget: 2 seconds of sprint in the tank, a hard lockout at empty until the bar refills to 100%, and a refill that only starts after 1 full second without sprinting and takes 3 seconds from empty. Held greedily, sprint uptime lands around 40%. The numbers were chosen against the NPCs: the crowd sprints in short seeded bursts, so a human who has to burst-and-recover now produces movement that looks like the crowd by default. Hiding got easier for players who manage the resource and harder for players who don't — the tank empties, the racer visibly slumps into a winded trudge, and that is a tell you created by being greedy.

Two design rulings keep it fair rather than fussy. Partial drains never lock you out — release Space above empty and it's available again instantly, so tap-management is rewarded, not punished. And the lockout ends generously: if Space is still held when the bar tops up, sprint resumes by itself on the ready pop, so nobody loses a race to a missed re-press.

The feedback had to be loud because the rule is invisible. The meter lives directly on the Space key in the control bar (the thing your thumb is already thinking about), its hue drains green to amber to red, bottoming out shakes the key and flashes the trough, the refill pulses so the wait reads as recharging rather than broken, and topping up fires a white pop that says "go" without requiring a glance. On the track, dust puffs and speed lines mark sprinting and a sweat drip marks exhaustion — so the state reads in the same place your eyes already are: the racers.

One engineering note: none of this touched the netcode. Remote players sync movementMode, and stamina gates movementMode locally before it ever leaves the client — an exhausted sprinter syncs as a walker, so every other client renders the correct speed for free.

How The Netcode Stays Smooth

The screen runs at 60fps. The network does not, and never needs to. The trick is dead reckoning: each frame, the client extrapolates a remote racer forward from its last synced progress and movement mode (the speed constants are shared), easing toward the target instead of snapping once per sync.

Live demo — snapping vs dead reckoning

Both clients receive the same updates at the sync rate you pick. The grey ghost is the true position. The red racer snaps to each update. The green racer dead-reckons: it keeps extrapolating between updates and eases onto corrections. Slow the sync rate down and watch the red one stutter while the green one stays believable.

The real frame loop src/App.jsx — createFrameLoop 
// Runs onFrame(dtMs, nowMs) every animation frame; falls back to a 16ms
// timeout where requestAnimationFrame is unavailable (jsdom). Returns a stop
// function.
const createFrameLoop = (onFrame) => {
  const usingRaf = typeof window.requestAnimationFrame === 'function'
  let handle = null
  let stopped = false
  let last = null
  const frame = (now) => {
    if (stopped) return
    const dt = last === null ? 0 : Math.min(Math.max(now - last, 0), MAX_FRAME_DT_MS)
    last = now
    onFrame(dt, now)
    schedule()
  }
  const schedule = () => {
    handle = usingRaf
      ? window.requestAnimationFrame(frame)
      : window.setTimeout(() => frame(performance.now()), FRAME_FALLBACK_MS)
  }
  schedule()
  return () => { stopped = true }
}
The real dead reckoning step src/App.jsx — remote racer extrapolation 
// Dead reckoning: advance remote racers every frame from their last synced
// progress and movement mode, easing toward the extrapolated target instead
// of snapping once per sync.
const speedPerMs = (MOVEMENT_SPEEDS_BY_MODE[snapshot.movementMode] ?? 0) / TICK_MS
const target = Math.min(
  snapshot.progress + speedPerMs * Math.max(now - snapshot.receivedAt, 0),
  NPC_MAX_PROGRESS,
)
const displayed = current[name]
let value = target
if (Number.isFinite(displayed) && Math.abs(target - displayed) <= REMOTE_SNAP_DISTANCE) {
  // small corrections ease over 150ms...
  value = displayed + (target - displayed) * Math.min(1, dt / REMOTE_BLEND_MS)
}
// ...large ones snap through (the if condition fails and value = target)

The rest of the pipeline keeps the network honest and cheap: input sends are event-driven, not fixed-rate. Movement-mode, lane, and firing changes send immediately; while nothing changes except progress, only a correction every 400ms goes out — dead reckoning fills the gap exactly because both sides share the speed constants. The final stretch (progress 85+) runs at the full 20Hz check rate so the server adjudicates the finish from fresh data, and aim never rides the periodic snapshot (it travels only with the shot). The Durable Object rebroadcasts compact deltas on a 50ms ticker that stops itself when traffic goes quiet, and the sockets use Cloudflare's hibernation API so idle rooms cost nothing.

Smoothness is a rendering trick layered on honest, lower-rate network state. Physical round-trip time to the room still exists; dead reckoning is what hides it.

The Durable Object Idea

A normal serverless function is like a front desk worker who forgets every conversation after answering it. That is fine for simple requests, but awkward for a live game room.

A Durable Object is different. It is more like assigning one room manager to one room code. Every request for DR1JLQ goes to the same coordinator. That coordinator can keep room state, schedule cleanup, and broadcast changes to connected sockets.

The entire routing trick workers/rooms.js — default export 
export default {
  async fetch(request, env) {
    const url = new URL(request.url)
    const roomCode = getRoomCodeFromPath(url.pathname)

    if (!roomCode) {
      return json({ error: 'Room code required' }, 400)
    }

    // Same room code -> same id -> same Durable Object, every time.
    const id = env.ROOM_LOBBY.idFromName(roomCode)
    const stub = env.ROOM_LOBBY.get(id)
    return stub.fetch(request)
  },
}

That is why Durable Objects fit this project: a room code naturally maps to one room owner, multiplayer state needs one official version, WebSockets need a place to live, and cleanup should happen even when players disappear.

Why React And Vite

React is good for this because the game currently has a lot of stateful UI: lobby controls, player rows, ready states, error panels, scoreboards, round states, conditional side panels, crosshairs, and reveal tags. Vite is fast and plain — it gives a tight local loop without making the project feel bigger than it is.

We did not reach for a heavy game engine because the first playable version is about proving the hidden-identity loop. A full engine can be helpful later, but early on it would mostly add ceremony. This game needed a clear track, clean input, and honest multiplayer state more than it needed a physics system.

Why DOM And CSS Instead Of Canvas

The earliest spec allowed a 2D canvas renderer. The current implementation uses DOM and CSS for the playfield. That was a practical choice: the game needed 20 readable lanes, pixel-style racers, crosshairs, bodies, reveal labels, a checkered finish line, and lots of UI around the track. CSS handles that well.

It also makes testing easier — the test suite can query lanes, buttons, labels, and markers directly. Even the juice (screen shake, the KO bounce, hit flashes) is pure CSS keyframes triggered by class changes, which means prefers-reduced-motion support is one media query instead of a rendering-engine feature.

Canvas may still be useful later if animation complexity grows or the art direction becomes more elaborate. But switching to canvas should be a response to pressure, not a reflex.

How The Animal Racer CSS Works

Every racer is three spans and zero images. The whole zoo — 8 species in 5 palettes, 40 distinct looks — is roughly 150 lines of CSS built from four tricks. These three are live, rendered by a copy of the game's sprite CSS:

cat · peach
bunny · sky
frog · mint

The box is the body. The base .racer element is a 22×25 bordered box whose background is the fur color — and that box is also the hitbox. .racer-head is a rounded face patch, .racer-body a belly patch. Nothing about a species changes the box, which is how the spec's "same hitbox for every variant" rule survives: a bunny with tall ears occupies exactly the same clickable area as a frog.

The box-shadow clone trick. A box-shadow with no blur is a pixel-perfect copy of the element's shape, offset by the shadow's distance — so every symmetric feature costs one element and one shadow, never two elements.

  height: 3px;

/* the same trick duplicates ears: */
.shape-1::before {            /* bunny */
  width: 4px; height: 8px;    /* one tall ear */
  background: var(--suit);
  box-shadow: 7px 0 0 var(--suit);  /* second ear, free */
}

Clip-path for the pointy bits. Triangular features — cat and fox ears, the chick's beak and tail feathers — are polygon cuts on small rectangles. One polygon cuts both cat ears out of a single strip:

Both cat ears from one strip src/App.css — .shape-0::before 
.shape-0::before {
  content: '';
  position: absolute;
  top: -5px;                  /* hangs above the box, hitbox unchanged */
  width: 16px;
  height: 5px;
  background: var(--suit);
  /* two triangles: up at 20% and 80%, notch between them */
  clip-path: polygon(0 100%, 20% 0, 40% 100%, 60% 100%, 80% 0, 100% 100%);
}

Species are pseudo-element slots. Each shape-N class fills up to three slots on the shared anatomy: ::before is the headgear (ears, eye bumps, tuft), ::after is usually the tail (hanging off the left, since racers run right), and .racer-head::after carries the face feature (bear muzzle, pig snout, mouse nose, chick beak, frog grin). Palettes are just three custom properties — --suit for fur, --head for face and belly, --trim for accents — swapped by the archetype-* class, so any species renders in any palette with no extra rules.

Two non-obvious constraints shaped this. First, the shape-N class names never changed even though the silhouettes did, because npcBehavior.js seeds each NPC's pacing personality from its shapeClass string — renaming the classes would have silently reshuffled every NPC's behavior. Second, everything composes with the existing states because it is all one element tree: the dead rotation, desaturation, hit flash, and step-bob animations apply to the same box the features hang off, so corpses keep their ears.

Pseudo-elements and unblurred box-shadows are a free sprite sheet. Before reaching for image assets or canvas, check how far "one box, three vars, and a few shadows" can go.

The Most Important Technical Decisions

1. Real Rooms, Not Fake UI

The project had early local/prototype behavior. That was useful while shaping the game, but became dangerous once the goal was "my friends can join and play." The rule now is simple: if the UI says there is a room, the backend room should exist. No placeholder room on GET, no joining before the host creates, join errors visible instead of silently entering a fake lobby.

2. Everyone Ready Means Everyone

The host can only start when every connected player, including the host, is ready. This rule lives in shared state logic, not scattered button checks. Buttons are allowed to explain and reflect the rule; the backend must enforce it.

The rule, in one place src/multiplayer/roomState.js — canStartRoom 
export function canStartRoom(room) {
  return (
    room.players.length > 0 &&
    room.players.every((player) => player.connected) &&
    room.players.some((player) => player.role === 'host') &&
    room.players.every((player) => player.ready)
  )
}

3. Host-Only Round Control

Only the host can start countdowns, advance live play, record round winners, show scoreboards, and start next rounds. Without that, every client becomes a little steering wheel — one enthusiastic guest could move the room forward before everyone else is ready.

Backend enforcement workers/rooms.js — countdown action 
if (action === 'countdown') {
  if (toPlayerId(body.playerName ?? '') !== room.hostId) {
    return json({ error: 'Only the host can start the game' }, 403)
  }
  if (!canStartRoom(room)) {
    return json({ error: 'Room is not ready' }, 400)
  }
  const nextRoom = startRoomCountdown(room)
  await this.saveRoom(nextRoom)
  return json({ room: serializeRoom(nextRoom) })
}

4. Heartbeats Are Per Player

A major cleanup bug came from the wrong kind of "touch." If every room request refreshed every player, disconnected players never looked stale. The fix was per-player heartbeats: each browser refreshes only its own timestamp, so the room can tell the difference between "Mia is still here" and "James clicked something."

5. Internal State Should Not Become UI Noise

The visible Sync status flickered between transport states like live and connected. Internally, that information helps with recovery. Visually, it was just noise. We kept the internal state and removed the visible flicker. Not every useful engineering detail deserves a place on screen — users need confidence, not a networking diary.

6. Kills Are Scored Where The Truth Lives

When kill points arrived (a round win is 3 points, a human kill is 1, NPC kills are worth nothing), the tempting shortcut was to let the shooting client declare "I killed Mia" — it already knows the lane assignments. We did not do that. The server resolves the victim from the freshest inputs: whichever connected player last claimed that lane is the human victim, anything else is an NPC. The shooter's client still scores optimistically for instant feedback, but the authoritative number always comes back from the room.

Server-side kill attribution src/multiplayer/roomState.js — recordRoomShot (excerpt) 
// The victim is resolved from the freshest inputs: a connected player whose
// controlled lane matches the shot lane is a human kill, anything else is
// an NPC. Lane assignments themselves only exist client-side.
const victimName =
  Object.entries(room.inputs ?? {}).find(
    ([playerName, input]) =>
      Number(input?.laneId) === numericLaneId &&
      room.players.some(
        (player) => player.name === playerName && player.connected,
      ),
  )?.[0] ?? null
const victimType = victimName ? 'human' : 'npc'

// Kill credit requires a fresh human takedown: no NPC farming, no points
// for shooting a corpse, no points for shooting yourself.
if (
  !laneAlreadyShot &&
  victimType === 'human' &&
  victimName !== shooterName &&
  Object.hasOwn(nextScores, shooterName)
) {
  nextScores[shooterName] += KILL_POINTS
  nextKills[shooterName] += 1
}

The same change forced a cleanup: room inputs now reset when a new round starts, because a stale lane claim from the previous round could have credited a kill against a player who was no longer in that lane. Stale inputs could also have mis-adjudicated a finish, so clearing them fixed a latent bug we had not hit yet.

The design rule for the juice itself: attribution must not leak hidden identity. A killer's name on the KO marker and kill feed reveals nothing about which lane the killer controls, and a victim's name is only revealed once they are already dead. The tension mechanic survives intact.

Bugs We Hit And What They Taught Us

Every serious bug here became a regression test. These are the ones worth remembering.

trustfrontend flow

The Hardcoded Room Problem

The UI behaved like the room was hardcoded — classic prototype residue. The screen looked interactive, but the mental model was still "local demo." The fix was to audit the button flow against the desired real flow: host creates, gets a code, a friend joins that exact room, everyone sees the same roster, everyone readies, host starts.

When a user gives you a flow, test against the flow, not against individual components. A button can work in isolation and still fail the story.
trustbackend

Placeholder Rooms

The Worker originally allowed missing rooms to appear through GET or join behavior. That made the UI feel like it worked, but it was not trustworthy. The fix: only the explicit create action creates a room; missing rooms now return Room not found.

Fake success is worse than honest failure. A clear error gives you something to fix. A fake room lets the bug put on a nice jacket and walk around.
deployapi routing

Production API Fallback

The deployed Pages app initially tried to call relative /api/rooms. That works in local dev — but the room backend is a separate deployed Worker with a different origin.

The fix src/multiplayer/api.js — getRoomsApiBase 
export function getRoomsApiBase(hostname = window.location.hostname) {
  if (import.meta.env.VITE_ROOMS_API_BASE) {
    return import.meta.env.VITE_ROOMS_API_BASE   // explicit override
  }
  if (!['localhost', '127.0.0.1', ''].includes(hostname)) {
    return PRODUCTION_API_BASE                   // deployed Pages -> deployed Worker
  }
  return DEFAULT_API_BASE                        // localhost -> /api/rooms
}
Local paths can lie. Production has origins, routing, CORS, and deployment boundaries. Always test the deployed shape.
deploybrowser rules

CORS Preflight

After the frontend pointed at the Worker, the browser still blocked requests because the Worker did not answer CORS preflight requests. The fix: CORS headers on JSON responses, an OPTIONS response for preflight, and Worker tests for both.

Postman and unit tests are not a browser. Browsers enforce rules that server-to-server tools do not. If the app runs in a browser, verify in a browser.
designsimulation

NPCs That Idled Forever

Early NPC calming went too far: NPCs spent ~40% of ticks stopped or idle-crawling, averaging 39% of a running player's speed. The fastest NPC finished in ~47 seconds against a ~21 second player — so anyone moving with intent was instantly identifiable as human. The fix flipped the model from "wandering extras" to "players": run-heavy pacing personalities with walk breaks and brief human-scale stops. Front-runner NPCs now finish in 23–24 seconds.

In a hidden-identity game, NPCs are not scenery. They are the crowd you hide in, so they must be statistically similar to the players.
designsimulation

The Crowd That Outran The Winded

Sprint stamina quietly rebalanced the whole race. NPC pacing had been tuned against a human who could hold sprint forever (~7.5 progress/s); once stamina capped a committed human at ~5.8, the untouched crowd was suddenly moving at 82% of the best possible human pace — and faster than any human who ever rested. Playtesting read as "the NPCs are racing," but nothing about the NPCs had changed. The humans had.

The fix was measured, not felt: a simulation replicating the exact NPC tick math showed the crowd at 4.76 progress/s against the walker's 5.0. A single NPC_PACE_SCALE = 0.6 on the NPC speed table brings the pack to ~2.9 progress/s — back to "roughly half a committed player" — finishing around 33 seconds against the human's 16, with every burst, stop, and personality intact. A regression test pins the median crowd racer's 8-second progress inside an amble band so no future speed change silently re-races the crowd.

A follow-up pass leaned into what the game had become: a hiding game. The scaled crowd still never stopped moving, so a human loitering to blend in stuck out against a pack of perpetual joggers. New pacing patterns and loiter rolls put the crowd at a full stop or an idle shuffle about 40% of the time (pace ~2.2 progress/s, finish ~42s). This deliberately walks back toward the "idled forever" territory above — the difference is that now the players also stop, so stillness reads as strategy instead of set dressing.

Pace is relative. Nerfing the player buffs everything you didn't touch, so retune the crowd against the player's new ceiling — and let a simulation, not vibes, pick the number.
audioweb audio

Music That Sounded Like Static

The first gameplay music sustained a square-wave bass and a sawtooth drone continuously under a fast minor-key note loop. Harsh waveforms held forever read as noise, not music. The fix: soft sine pads holding a Cmaj7/Am7/Dm7/G7 progression, a gentle triangle melody at a relaxed beat, and a quiet bass note on each chord change.

Generated audio is cheap to ship and easy to get wrong. Waveform choice and envelope shape matter more than the notes.
correctnessrendering

Corpses That Teleported Back To The Start

Eliminated racers were supposed to stay where they fell. Instead, getLiveProgress returned racer.progress — the lane's starting position — for any shot racer, so a corpse dropped at 60% of the track instantly teleported back to its spawn point. Nobody had noticed because most eliminations happened early, near the start positions.

const getLiveProgress = useCallback(racer => {
  if (shotRacerIds.includes(racer.id)) {
    return racer.progress   // BUG: this is the lane's STARTING position,
  }                         // so every corpse snaps back to spawn
  // ...live sources for racers still racing
})
// Dead racers freeze at the progress captured when the hit landed instead
// of snapping back to the lane start position.
const getLiveProgress = useCallback(racer => {
  if (shotRacerIds.includes(racer.id)) {

    return Number.isFinite(frozenProgress)
      ? frozenProgress          // captured at hit time (shooter) or
      : getTrackProgress(racer) // sync time (everyone else)
  }

A wrong value that is usually close to the right value can hide for a long time. The bug only became visible once we went looking at kills that landed mid-track.

The Corpse That Came Back To The Start Line

The corpse fix above had a sequel. A playtest showed one shot NPC frozen correctly mid-track and another standing dead at the start line — timing-dependent, so it smelled like a race. It was one. The killer detail: the client resets its round state the moment the host clicks "Next round", but the network does not stop delivering messages that were already in flight.

// the failure, as a timeline
t0  host clicks "Next round"
t1  client resets: corpses cleared, NPC positions rebuilt AT THE START LINE,
    seen-lanes set emptied, local round -> 2
t2  a snapshot from round 1 (sent before t0) finally arrives
t3  client applies its old shotRacerIds -> lane 12 "dies" again
t4  the death effect captures lane 12's current position...
    which the reset just rebuilt to the START LINE
t5  lane 12 is now marked "seen", so when it is shot for real in
    round 2: no KO marker, corpse rendered at the start line

Two layered fixes. The first is a version check: every snapshot carries the server's round number, so anything older than the client's current round is rejected before it can touch any state. The second makes the bookkeeping self-healing, so even a same-round revert (stale response inside one round) cannot leave poison behind.

Fix 1 — reject snapshots from the past src/App.jsx — room sync effect 
// In-flight snapshots from a round that already ended locally must be
// dropped whole: applying their shotRacerIds after resetRoundState used
// to re-freeze old corpses at the rebuilt start positions and mark those
// lanes as already seen.
if (Number.isFinite(roomSnapshot.round) && roomSnapshot.round < currentRound) {
  return
}
Fix 2 — self-healing death bookkeeping src/App.jsx — death detection effect 
// Self-heal when a lane un-dies (a stale snapshot briefly reverting a
// kill): forget its bookkeeping so a later kill on the same lane
// re-captures a fresh position and pops its KO again.
const activeShotLanes = new Set(shotRacerIds)
const revivedLaneIds = [...seenLanes].filter(
  (laneId) => !activeShotLanes.has(laneId),
)
if (revivedLaneIds.length) {
  revivedLaneIds.forEach((laneId) => seenLanes.delete(laneId))
  setDeathProgressByLane(current => {
    const next = { ...current }
    for (const laneId of revivedLaneIds) {
      delete next[laneId]
    }
    return next
  })
}

Why both? Fix 1 alone closes the cross-round race but not a same-round revert; fix 2 alone heals the poisoning but lets the stale corpse flash on screen first. Belt and braces: reject what you can identify as stale, and make everything else recoverable.

In a distributed system, messages arrive from the past. Any state reset needs a version check on incoming data, or the past will overwrite the present.

The Shuffle That Favored Low Bits

Lane assignments come from a seeded Fisher-Yates shuffle so every client derives the same secret lanes. The swap index was computed as state % (index + 1) from a linear congruential generator — and an LCG's low bits are its worst bits: the lowest bit just alternates, the bottom k bits cycle with period 2k, and a modulo mostly reads those low bits. The result was a patterned shuffle — deterministic and shared, but not fair.

The one-line fix src/App.jsx — shuffleWithSeed 
state = (Math.imul(state, 1664525) + 1013904223) >>> 0
// Scale from the high bits: an LCG's low bits cycle with tiny periods
// (the lowest bit just alternates), so `state % n` produced patterned
// lane assignments instead of a fair shuffle.
const swapIndex = Math.floor((state / 4294967296) * (index + 1))

A regression test pins fairness: 400 seeded rooms, every lane must appear as the host lane, none may dominate, and the lane must reshuffle between rounds.

With an LCG, take bits from the top. state % n is the classic trap; the high bits are where the randomness lives.

The Round That Froze On Go

Round 3 of 5: the countdown hit "go" and nothing happened, for anyone, forever. The host's client sends the playing action when the countdown completes, guarded by a fire-once flag so it does not spam the server — but the flag was set before the request resolved. When that one request failed, the flag stayed set, nothing retried, and since only the host may advance the phase, every client in the room was stranded on "go".

The fix — retry until the phase turns src/App.jsx — countdown effect 
playingRequested.current = true
// A failed request must not strand every client on "go": clear the
// flag so the 100ms countdown ticker retries until the phase turns.
void syncRoom('playing', { playerName: activePlayerName }).then((room) => {
  if (!room) {
    playingRequested.current = false
  }
})
A fire-once flag is a promise to eventually fire. Set it optimistically and a single failure turns "fire once" into "fire never" — clear it on failure, or set it only on success.

The Match That Refused To End

Winning the final round showed the final scores for a heartbeat, then dumped the player back to the scoreboard. Two independent causes stacked:

  • The server has no gameOver phase. It parks on roundOver/scoreboard after the last round. The client's phase sync faithfully mirrored whatever the server said — so the very next heartbeat snapshot yanked a locally-finished client straight back into the round loop. Final scores appeared for exactly one sync interval, then vanished.
  • Joiners never adopted the host's round count. roundCount was serialized in every room snapshot, but no client ever read it back. A guest in a 3-round match kept the default of 5, so their "is the match complete?" check disagreed with the host's and they never saw a final-scores action at all.
Fix 1 — a truce between local gameOver and server phases src/App.jsx — room sync effect 
if (['playing', 'roundOver', 'scoreboard'].includes(roomSnapshot.phase)) {
  setState(current => {
    // The server has no gameOver phase; once the match completes locally,
    // late roundOver/scoreboard snapshots must not yank the player out of
    // the final-scores screen back into the round loop.
    if (
      current === 'gameOver' &&
      ['roundOver', 'scoreboard'].includes(roomSnapshot.phase)
    ) {
      return current
    }
    return current === roomSnapshot.phase ? current : roomSnapshot.phase
  })
}
Fix 2 — adopt the host's round count src/App.jsx — room sync effect 
// Joiners must adopt the host's round count or their match-complete
// check disagrees with the host's and the final scores never show.
if (roomSnapshot.roundCount && roomSnapshot.roundCount !== roundCount) {
  setRoundCount(roomSnapshot.roundCount)
}

The regression test for this bug advertises a 1-round match from the mock server, wins it, clicks "Show final scores", then lets more roundOver-phase snapshots arrive — and asserts the final-scores screen is still standing. The test passing also proves round-count adoption, because the client only offers "Show final scores" if it agrees the match is over.

Purely client-side states need an explicit truce with server sync. If the server does not know a state exists, the sync code must be told not to stomp it.

The Shot That Erased Your Lane Claim

The firing input sent only playerName, movementMode, aim, and firing. Server-side, setPlayerInputState replaces a player's whole input entry — so firing overwrote your laneId with null and your progress with 0. For the ~50ms until your next periodic input, the server had no idea which lane you controlled: a return shot into your lane in that window would have been attributed as an NPC kill, and a finish could not be adjudicated for you.

The fix spreads the latest full snapshot into the firing input so the lane claim survives, with a regression test that inspects the actual request payload.

When the server replaces state wholesale, every sender must send the whole truth. Partial updates against replace-semantics are silent data loss.

Host Leave, Abandoned Tabs, And Room Destruction

Rooms needed to die when the host leaves or everyone disconnects — otherwise old rooms linger, confuse players, and bill forever. The layers: host-leave detection, per-player heartbeats, cleanup alarms, a closed-room UI state, and an idle rule where heartbeats keep a player connected but deliberately do not count as room activity.

Liveness vs activity src/multiplayer/roomState.js — isRoomIdleExpired 
// Idle expiry uses lastActivityAt, which only meaningful actions refresh —
// heartbeats deliberately do not count, so an abandoned-but-open tab cannot
// keep a room alive forever.
export function isRoomIdleExpired(room, idleTtlMs, now = Date.now()) {
  const lastActivity =
    Date.parse(room.lastActivityAt ?? room.updatedAt ?? room.createdAt ?? '') || 0
  return now - lastActivity > idleTtlMs
}
Liveness and activity are different signals. A heartbeat proves the tab exists, not that anyone is playing. Timeouts should key off intent, and the server, not the client, must own the final cutoff.

The Honest Network Review

The first networking milestone was real and valuable: two friends could enter the same room code, see the same lobby, ready up, race, shoot, and advance rounds. That replaced a fake local prototype with an actual shared game. But reaching that milestone also exposed a deeper truth: transport is not authority. A WebSocket can deliver a message quickly while still delivering a lie.

One room, one owner

A room code maps naturally to one Durable Object. That removed cross-process locking and gave the lobby one official clipboard.

Global routing

Friends could reach the game without us operating a conventional server or load balancer.

Hibernatable sockets

Idle sockets can stay connected while the object leaves memory, reducing duration charges when a room goes quiet.

Fast prototype deployment

Pages, Workers, storage, alarms, and WebSockets were available under one account and one deployment tool.

Memory is conditional

Hibernation can recreate the object. High-frequency input kept only in memory is therefore not durable game truth.

Timers fight hibernation

A realtime simulation wants a stable clock. A serverless actor wants to sleep whenever possible. Both goals are reasonable, but they pull in opposite directions.

Runtime-specific plumbing

Alarms, socket attachments, compatibility dates, storage semantics, and Worker deployment concerns became part of ordinary game logic.

Harder local reasoning

The browser, Worker router, Durable Object lifecycle, persisted room, in-memory inputs, and fallback polling all have to agree before one racer looks smooth.

Identity

Moving hosts does not magically authenticate players. We still need unguessable sessions bound to connections.

Cheating

Colyseus cannot help if the server continues accepting a client-authored position, target, or winner.

Game rules

Race movement, stamina, shots, scoring, NPC behavior, and finish adjudication still need explicit deterministic rules.

Testing discipline

A new framework can reduce plumbing, but only adversarial and multi-client tests prove that the room is fair.

The Trust Problem Hidden Inside A Friendly Prototype

Today, a player is largely identified by a display name supplied by the browser. The socket URL contains that name, messages can carry another name, and several HTTP actions trust the name in their body. Host checks then ask whether that supplied name hashes to the host ID. In a friendly test this feels like identity. On a network it is closer to wearing someone else's handwritten name tag.

Current claimWhy it is unsafeTarget rule
"I am James"The browser supplies the nameThe server issues a random session token and binds it to the connection
"I control lane 7"The browser supplies the laneThe server privately assigns the lane and never publishes the full assignment map
"My progress is 100"The browser supplies progressThe browser sends movement intent; the server advances position
"I hit lane 12"The browser decides whether the shot hitThe browser sends aim; the server resolves geometry against official positions
"This NPC won"The host reports client-simulated NPC resultsThe server simulates NPCs and adjudicates every winner

The Reliability Problem

The current client falls back to polling when its WebSocket closes, but it does not schedule a socket reconnection. A momentary Wi-Fi interruption can quietly turn into ten-second updates for the rest of the match. Inputs also lack a strict round-and-sequence envelope at the point they are applied, so stale or reordered traffic is harder to reject with confidence.

The replacement protocol needs four boring fields that prevent exciting bugs: protocolVersion, roundId, sequence, and a server timestamp. The server should acknowledge durable events with unique event IDs so a reconnect cannot replay a gunshot, kill, winner celebration, or score animation.

The most dangerous multiplayer bugs are grammatically valid messages sent by the wrong person, in the wrong round, at the wrong time. Validate identity, authority, phase, ordering, and bounds before changing state.

Why Colyseus Instead Of More Custom Socket Code?

We have already hand-built rooms, joins, leaves, snapshots, compact deltas, socket lifecycle, fallback polling, cleanup, and tests around all of them. Those are exactly the responsibilities Colyseus is designed to standardize. It gives each connection a session identity, models isolated rooms, disposes empty rooms, rate-limits messages, and synchronizes changed state at a configurable patch rate.

The valuable boundary is this: the client sends a request such as walk, sprint, or fire at x/y. Only the room mutates official state. Colyseus can encode and distribute those mutations efficiently, but our room code still decides whether each request is legal.

Why Fly.io Instead Of Another Serverless Host?

A tiny Fly machine is conceptually simple: while matches exist, one Node process exists. That lets the server run a fixed-step clock, retain room inputs, and handle reconnect grace periods without translating everything into storage writes or alarm semantics. It also gives us a predictable small-machine cost rather than billing shaped around every message and active object duration.

There is a tradeoff. A conventional process can restart, deploys can interrupt rooms, and scaling beyond one machine eventually requires room-aware routing or presence infrastructure. For this project, those are honest future problems. We should solve the current friend-scale game clearly before optimizing for an audience we do not have.

Colyseus documentation describes server-owned state with property-level synchronization, and Fly documents per-second machine billing plus autostart/autostop controls. Fly does not currently provide native billing alerts, so this side project uses scale-to-zero, one 256 MB machine, no volume, and manual billing checks instead of pretending an alert exists.

A big-bang rewrite would make every failure ambiguous. Was the lobby wrong, the protocol wrong, prediction wrong, Fly misconfigured, or Colyseus misunderstood? The safer sequence keeps the current game playable while replacing one source of truth at a time.

Why Failing Tests Are Part Of The Estimate

For each migration task, the agent should first write the test that demonstrates the missing guarantee. The host-impersonation test should succeed at attacking the old design, then fail against the new session model. The teleport test should prove that sending progress cannot move the server racer. The duplicate-shot test should prove that replaying a packet cannot spend two bullets or award two kills.

This is not ceremony. A migration changes enough code that a passing old suite can become misleading: it may only prove that the old architecture still behaves like itself. New tests describe the guarantees we are moving for.

Migrate behavior, not files. Keep a runnable game at every boundary, prove one authority rule at a time, and delete the old transport only after the new path survives a real multi-browser match.

Migration Field Notes: What The Running System Taught Us

This is the part of the guide that grows with the migration. Plans explain what we expect; field notes record what the deployed software proved, including the moments where a green local suite was not enough.

Reconnect Is A State Transition, Not A New Login

A dropped WebSocket does not mean the player disappeared. The server keeps the authenticated player and secret lane alive for a 45-second grace window, while the client presents a rotating 256-bit reconnection token. A successful resume must restore the same player, the same private lane, the current round, and the latest authoritative snapshot. Creating a new player would look connected while quietly corrupting the match.

The live proof server/remoteSmoke.js 
const guestPlayerId = findPlayerForSession(guest.sessionId)
const resumed = waitForReconnect(guest)
guest.connection.close() // unexpected network drop
await resumed
await waitFor(() => guest.state.players.get(guestPlayerId)?.connected === true)

The public Fly smoke now creates two clients, joins by shared code, forces one connection to drop, waits for Colyseus to resume it, then starts the race and proves authoritative movement still reaches the other client.

Reconnect is continuity. Test identity and private state after recovery, not merely whether a socket opened again.

Bad Networks Need A Deterministic Test

Latency and jitter are timing; duplication and reordering are ordering; packet loss is absence. A useful regression turns all five into a fixed delivery schedule. The server accepts a monotonically newer command once, rejects old copies, and never fills in a missing command by trusting client-authored progress.

This is why every command carries a room ID, round ID, and increasing sequence number. A packet can contain perfectly valid JSON and still belong to yesterday's round or arrive after its replacement.

Do not test a network by hoping the test runner is slow today. Build a small, deterministic hostile network and assert the state left behind.

Audio Nodes Are Resources, Not Just Effects

The earlier game lost music after round one because lifecycle state and sound state drifted apart. A stopped oscillator cannot be restarted. If a stale reference says “music exists,” the next round remains silent even though every UI flag looks right.

The Colyseus client now owns one browser audio context, creates a fresh music graph whenever authoritative state enters playing, stops and clears that graph when the round ends, and closes everything on unmount. Shot audio is immediate and local, so it feels responsive without adding a single game-server message.

For timers, sockets, animation frames, and audio nodes, cleanup is half the feature. Test start → stop → start again, because the second run finds lifecycle bugs the first run cannot.

Public, Private, And Server-Only Are Different Products

Shared crosshairs sound simple until hidden identity enters the room. Everyone needs to see where every loaded weapon is aiming, but nobody should receive “James controls lane 7.” The server therefore publishes anonymous, per-round crosshair IDs with aim coordinates, color, and bullet state. The authenticated connection separately receives its own crosshair ID, controlled lane, stamina, exhaustion, and elimination state. The player-to-lane map never enters synchronized public state.

One room, three visibility levels server/DeathRaceRoom.js 
// Public: enough for every browser to draw the same aim marker.
crosshair = { id, aimX, aimY, colorIndex, hasBullet }

// Private: sent only to the authenticated connection.
privateState = { playerId, laneId, crosshairId, stamina, exhausted, eliminated }

// Server-only: authorization and the hidden assignment relationship.
crosshairIdByPlayerId.set(playerId, crosshairId)

Stamina updates travel on the same private channel and are stripped from the low-frequency React metadata projection. Only the isolated track subtree receives rapid racer, crosshair, and stamina views, so a moving mouse does not rerender the lobby shell or scoreboard.

Privacy is not “do not draw this field.” If the browser receives a secret, a curious player can read it. Design separate state channels and test the serialized public shape.

Randomize The Costume, Preserve The Collision Box

The migration prototype temporarily replaced the game's animals with circles, diamonds, and triangles. That was mechanically playable but not behaviorally equivalent: character variety is camouflage in a game where players are trying to disappear into the crowd.

The Colyseus track now derives eight species and five pastel palettes from room, round, and lane. A lane gets a different-looking costume in later rounds, every set of twenty contains all species and palettes, and no appearance value depends on whether its controller is human or NPC. Ears, tails, snouts, and beaks are CSS pseudo-elements outside one shared bordered body, so silhouettes vary while the hit window stays identical.

Starting progress is also randomized inside a deliberately narrow 1.5–3.5% band. That breaks the visual stack at the left edge without turning spawn luck into a meaningful racing advantage. Adding non-zero decimal starts revealed two old tests that equated “server did not accept a teleport” with “progress remains below 2.” The stronger assertions now compare movement delta from the authoritative start with a floating-point tolerance, which tests the security rule without assuming a particular presentation or exact binary representation.

A robust test asserts the invariant, not yesterday's convenient initial value. Here the invariant is “client progress is ignored and server movement adds the legal delta,” not “every racer begins at zero.”

A Reveal Is A Permission Change

During play, the player-to-lane relationship is a secret. After the server locks the first winner, that same relationship becomes the point of the round: everyone wants to see who fooled them. The reveal is therefore not a client animation guessing from local history; it is an authoritative permission change at one exact phase boundary.

Each public racer starts with an empty revealedName. When a human or NPC crosses the official finish threshold, the room awards points, records the winner, fills names only for human-controlled racers, and changes phase to roundOver in the same simulation step. The client then presents the frozen 20-lane track beside the scoreboard. An NPC winner gets the shame message, while a human winner gets the ordinary reveal.

The track component also had to be able to mount after simulation stopped. High-frequency views normally arrive before low-frequency React metadata, so a newly mounted result track could miss the final racer snapshot and stay empty forever. The transport now retains its latest projected view for phase-boundary mounts without subscribing the whole shell to 20 Hz updates.

When information changes from secret to public, let the authority publish that transition atomically. And when a UI mounts after the stream goes quiet, give it the last value, not only a future subscription.

Connected Does Not Mean Present

A WebSocket can remain healthy in an abandoned laptop tab. Protocol pings prove that a network path exists; they do not prove that a person is still playing. Keeping those rooms alive forever wastes Fly runtime, leaves stale codes in memory, and makes the roster lie.

The migration now has two independent safety limits. The browser resets a 20-minute timer only on real pointer or keyboard activity, then voluntarily leaves when it expires. The authoritative room tracks accepted game commands as meaningful activity and closes after 30 minutes even if clients or browser timers misbehave. Host departure uses the same server-owned closure path.

Closure is a first-class protocol event with a reason. Clients that receive host-left or idle-expired stop reconnecting, show a stable Room closed view, and offer one Return to menu action. Treating that event like an unexplained socket drop would launch reconnect retries against a room that intentionally no longer exists.

Liveness answers “can these machines still talk?” Activity answers “is anyone still using the product?” Give them separate clocks, and make intentional shutdown distinguishable from failure.

Controls Are State, Not Individual Key Events

A naive controller translates every keydown into movement and every keyup into stop. That fails the moment keys overlap: hold Right Arrow, press Space to sprint, then release Space while still holding Right Arrow. “Key up means stop” freezes the racer even though the player is still asking to walk.

The migration client now keeps a set of held movement keys and derives one intent from the whole set: Space wins as sprint, otherwise Right Arrow means walk, otherwise stop. It sends only when that derived mode changes. The same state drives the physical control highlights, so the HUD cannot disagree with the command stream. Input and select elements are excluded before either keydown or keyup changes the set.

The final countdown label follows the same principle of deriving presentation from authority. Every browser computes 3, 2, 1, and a brief Go from the server's countdownEndsAt timestamp; there is no independent client countdown that can drift into a frozen round.

For chords and overlapping inputs, model what is held and derive intent. Events tell you what changed; state tells you what the player means now.

Test The Match, Not Just The Messages

The first hosted smoke test proved that two browsers could connect, reconnect, ready up, and move one racer. Those were useful facts, but they did not prove that Death Race worked. A broken finish threshold, stale round number, missing score transition, or room that never disposed could all hide behind that green result.

The Fly smoke now tells a complete three-round story. A guest reconnects as the same authenticated player; the host shoots that guest and earns one point; the host crosses the authoritative finish three times for nine more points; each Next round command uses the server's current round number; the match reaches game over with ten points; then both clients leave and the old code becomes unjoinable.

This found an important weakness in the harness itself: its command helper had hardcoded roundId: 1. That was invisible while the test stopped in round one. Extending the scenario forced the test client to obey the same stale-round rules as a real browser.

A protocol test proves individual rules. An end-to-end test proves that the rules compose into the experience a player was promised. Keep both, because neither can replace the other.

Deployment Is Part Of The Test Surface

The current migration path is live behind a stable preview alias while the existing Cloudflare-backed game remains untouched. A 1280×720 browser acceptance pass proved all 20 racers fit with no document scrolling, the sound control remains outside the track, and the public page talks to the Fly WebSocket endpoint. The immutable deployment URL gives each step a precise artifact; the alias gives playtesters one address to remember.

A feature is not deployed because the build command succeeded. Exercise the hosted frontend against the hosted server and inspect the actual laptop viewport.

The guide itself supplied a smaller version of the same lesson. The repo once had a tested 113 KB root guide and a stale 50 KB public copy, so green tests and successful deployment still served old teaching material. The fix was one canonical lowercase why.html Vite entry plus a regression that forbids the duplicate. The guide now uses Cache-Control: no-cache, while hashed game assets remain immutable.

The Next Layer Of Juice

Juice is the tiny sensory evidence that tells a player, "yes, the game understood you." It is not decoration pasted over uncertain rules. The shot tracer is satisfying because it follows an accepted shot. The winner burst is satisfying because the room has locked one winner. Networking and juice meet at exactly this point: effects need authoritative event IDs, but they should render locally without producing more network traffic.

Start anticipation · 2-3h

Escalating tones, crouched racers, a small camera push, and a shared dust release on Go. Every client derives it from the same countdown timestamp.

Shooting feedback · 2-4h

Immediate muzzle flash and recoil, followed by an authoritative tracer impact, casing spark, and near-miss sound. No pre-shot target highlighting.

Finish celebration · 2-4h

A short hit-stop, checkered burst, winner bounce, crowd swell, and restrained camera punch triggered once by the winner event ID.

Round reveal · 2-3h

Reveal human racers sequentially, then animate kills and points into the scoreboard while keeping Next round visible on a laptop.

Track atmosphere · 2-4h

Subtle lane motion, varied dust, footsteps, exhausted breathing, finish-line flutter, and music intensity in the final third.

The Hidden-Identity Constraint

A normal racing game can make the local player glow, leave a unique trail, or receive richer animation. Death Race cannot do that publicly without damaging its central mystery. Humans and NPCs must produce the same visible movement cues for the same official movement mode. Local-only feedback may be richer on the controlling player's own screen, but spectators must not be able to identify a human from an exclusive dust puff, cadence, sound, or animation.

The Laptop Constraint

More effects must not mean more interface. The game should continue to fit twenty lanes and core lobby actions on a laptop without page or sidebar scrolling. Particles belong inside stable playfield bounds; winner and score transitions must not push buttons below the fold; controls should become denser before they become scrollable.

The Accessibility And Replay Constraint

Every shake, hit-stop, and bouncing marker needs a reduced-motion form. Every sound respects mute. Every network-driven effect needs deduplication so reconnecting or receiving a repeated snapshot cannot replay a gunshot, KO, point award, or celebration. Every timer must clean itself up between rounds.

The juice backlog is estimated at 10-18 agent-hours, separate from migration. Start and finish effects should wait until the authoritative event protocol exists; track atmosphere can proceed independently because it is client-only.

What Is Still Prototype-Shaped

The game is real enough for friends to join and play, but it is not hardened like a competitive production game. Important caveats:

  • The client still renders and participates heavily in gameplay simulation, including all NPC simulation.
  • Hidden assignments are deterministic and client-derived — fine for friendly testing, not secure against inspection.
  • Human finishes and kills are adjudicated server-side, but identity is still just a player name, so it is not hardened against impersonation.
  • No accounts or persistent player identity exist yet; mobile and tablet controls are deferred.

That is not a failure. It is an honest stage. The project is now past fake multiplayer and into real playtest territory.

How Good Engineers Think Through This Project

  • They protect the core experience. The core experience is not "use WebSockets" or "deploy to Cloudflare." It is hidden-identity racing with one shot. Good engineering keeps asking: does this change make that experience clearer, fairer, faster, or easier to test?
  • They separate design truth from work logs. spec.md says what the game should be, todo.md what remains, progress.md what happened, WHY.md why it is shaped this way. That split prevents stale plans from masquerading as current truth.
  • They replace fake features with honest features. The lobby improved when we stopped accepting "looks like a lobby" and demanded "a second browser can join this lobby by code."
  • They make bugs pay rent. Every serious bug became a regression test. A bug without a test is a story you might have to relive.
  • They verify where the risk lives. Unit tests for local logic, Testing Library for UI, Worker tests plus real deploys for Cloudflare behavior — and two actual browser sessions against the deployed URL for "friends can join," because that was the user's real requirement.

Lessons To Carry Forward

Multiplayer Is Mostly State Discipline

The hard part is not opening a socket. The hard part is deciding who is allowed to change what, when, and how everyone else learns about it. In Death Race: the room owns the roster, readiness, shots, kills, and winners; the host controls phase transitions; clients render and send input. That boundary is what keeps the game understandable.

The Backend Should Enforce The Rules

A disabled button is nice. A backend check is necessary. The UI can hide Start game from guests, but the Worker still rejects non-host countdown requests. Frontend constraints help honest users. Backend constraints protect the state.

Small Modules Beat Grand Architecture

roomState.js is the right abstraction size: not a framework, just the shared room rules in one place. Easy to test, easy to import in the Worker, hard for frontend and backend rules to drift apart.

Write Tests For The Behavior You Fear Losing

The best regression tests came directly from scary bugs: "clicking anywhere gets a kill," "host leaves but room still exists," "CORS blocks the browser," "corpses teleport home." Those are not abstract correctness tests. They are memory aids: this hurt once, do not let it hurt again.

Future Pitfalls And How To Avoid Them

  • Cheating and hidden information. Hidden identity is presentation-level secrecy today. For competitive play, hidden assignments and authoritative simulation must move deeper into the backend. Decide the trust model early.
  • Latency and fairness. Distant players may need server timestamps or reconciliation around when a shot counts. Do not solve it before real playtests demand it — but do not forget it exists.
  • Room cleanup. Heartbeats and alarms are the first layer; future work may need stronger reconnection and "rejoin as the same player" flows.
  • State explosion. App.jsx can become too crowded as features arrive. Likely future extractions: gameplay simulation helpers, round transition hooks, input sync hooks, lobby and scoreboard components. Extract when the behavior has settled enough that the boundary is obvious.

The Best Mental Model

Death Race is a party game with a race track, a referee, and a radio.

  • The track is what players see.
  • The referee is the authoritative room simulation. Today it is split between clients and a Durable Object; the migration puts it in one Colyseus room.
  • The radio is the WebSocket carrying intentions toward the referee and official events back to everyone.

When the game feels good, players should forget the referee and radio exist. They should only feel the tension of twenty racers, one secret identity, one bullet, and a finish line that suddenly feels much too far away.

That is why the architecture matters. Not because Cloudflare, Fly.io, or Colyseus is fashionable. Not because WebSockets are exciting. Because the technology should make the rules feel inevitable and then disappear behind the suspicion.
